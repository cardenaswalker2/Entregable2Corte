Fundamentación Académica

Evolución y Alcance de ClinicaApp

Una respuesta tecnológica integral a las limitaciones estructurales en la gestión veterinaria urbana de Cartagena de Indias.

Contexto y Justificación Interdisciplinar

  • Relevancia Social: Los animales de compañía representan miembros plenos de los núcleos familiares urbanos contemporáneos.
  • Problemática Real: Uso preponderante de carnets físicos de vacunación, fichas en papel y bases de datos aisladas en cada centro asistencial.
  • Riesgo Sanitario: Pérdida de historiales preventivos vitales ante emergencias o traslados en el Distrito de Cartagena.
  • Marco Normativo: Cumplimiento estricto del Art. 15 CP, Ley 1581 de 2012 (Habeas Data), Ley 1774 de 2016 (Bienestar Animal) y Lineamientos CONPES 3975 de IA ética.

Objetivo General de Investigación

Desarrollar y evaluar una plataforma web integral e inteligente («ClinicaApp») para la gestión unificada de centros veterinarios en Cartagena, que integre un agente conversacional basado en Modelos de Lenguaje Masivos (LLM) con arquitectura segura en Spring Boot, un modelo analítico dimensional con identificación de fuentes de datos, y un modelo de optimización matemática para la asignación geoespacial de recursos clínicos.

Enfoque Metodológico: Paradigma empírico-analítico mixto (cualitativo en diseño de requerimientos y cuantitativo en tiempos de inferencia, consultas dimensionales y optimización algorítmica).

Desarrollo Web Avanzado: Arquitectura Spring Boot, LLM Nova Brain y Seguridad

Docente: Ing. Fabio García Ramírez 📄 Ver Entregable DWA (.pdf)

Implementación en Java 21 LTS y Spring Boot 3.5 con persistencia documental NoSQL y servicios de inteligencia artificial generativa.

1. Arquitectura de Integración con LLM (Nova Brain)

  • Controlador RESTful: NovaAIController.java mapeado al endpoint /api/nova-brain/think.
  • RAG Contextual Ligero: Al recibir una consulta, extrae la identidad del usuario desde Spring Security, consulta en MongoDB sus mascotas e historial de citas pendientes e inyecta dinámicamente este contexto en el prompt del sistema.
  • Proveedor Externo: Petición HTTP al endpoint de Groq Cloud consumiendo el modelo masivo Llama 3.3 70B Versatile gestionado mediante la variable ${GROQ_API_KEY}.
  • Motor de Contingencia Heurístico: Mecanismo fallback por expresiones regulares (MOTOR_LOGICO) que opera ante fallas de red o ausencia de credenciales externas.
  • Auditoría: Persistencia en LogInferencia.java registrando tokens consumidos, latencia y modelo.

2. Seguridad Perimetral, RBAC y Biometría

  • SecurityConfig.java: Configuración de SecurityFilterChain con encriptación BCrypt.
  • Filtros de Red: NetworkDeviceFilter y MaintenanceFilter para protección perimetral.
  • Autenticación Federada: OAuth2 / OIDC con Google y GitHub.
  • Control de Acceso RBAC: 6 roles (ROLE_ADMIN, ROLE_CLINICA, ROLE_VETERINARIO, ROLE_RECEPCIONISTA, ROLE_AUXILIAR, ROLE_CLIENTE).
  • Login Facial Biométrico: Algoritmo en UsuarioServiceImpl.java con distancia euclidiana sobre vectores de 128 dimensiones (umbral < 0.38).

Visualización de Datos II: Fuentes, Modelo Kimball y Preparación para Power BI

Docente: Ing. Walter Alberto Espriella Castellar 📄 Ver Entregable VD II (.pdf)

Estructuración de fuentes de datos, diseño del esquema estrella y repositorio sintético con 3.469 hechos simulados conforme a la Ley 1581 de 2012.

1. Caracterización Formal de Fuentes de Datos

  • Fuentes Operacionales (OLTP): Base de datos MongoDB Atlas 7.0 (colecciones usuarios, mascotas, clínicas, citas, servicios, visitas y logs_inferencia). Mecanismo de acceso: MongoRepository y Aggregation Framework.
  • Fuentes Sintéticas de Prueba (CSV): 6 datasets normalizados ubicados en docs/powerbi_datawarehouse/. Creados para validar analítica sin vulnerar la privacidad de usuarios reales.
  • Mecanismo de Acceso: Conector de texto/CSV nativo en Power BI Desktop y librerías de análisis en Python (Pandas).

2. Arquitectura del Esquema Estrella (Star Schema)

  • Metodología Ralph Kimball: Selección de esquema estrella desnormalizado para optimizar consultas de agregación y evitar JOINs lentos.
  • Tabla Central: Fact_Atenciones_Citas con grano atómico por cita individual atendida (3.469 hechos).
  • 5 Tablas Dimensionales: Dim_Tiempo (730 días), Dim_Clinica (6 sedes), Dim_Servicio (8 servicios), Dim_Mascota (150 animales), Dim_Veterinario (10 especialistas).
  • Relaciones: Uno a muchos (1:N) estrictas con filtrado unidireccional desde dimensiones hacia hechos.

3. Fórmulas DAX y Métricas Clave de Rendimiento para Power BI

Tasa de Asistencia:
[Total Citas Asistidas] / [Total Citas Programadas]
Tasa de Inasistencia (No-Show):
[Total Citas No Asistidas] / [Total Citas Programadas]
Ingresos Netos Totales:
SUM(Fact_Atenciones_Citas[monto_neto])
Adopción Canales Digitales:
[Citas por Nova AI + PLEB] / [Total Citas]
Nota de Rigor Académico: Se aclara explícitamente que este modelo dimensional corresponde a un prototipo analítico validado mediante el dataset sintético/de prueba de 3.469 hechos, diseñado específicamente para demostrar la viabilidad analítica y dejar la estructura preparada para su consumo en Power BI sin constituir aún un cuadro de mando productivo conectado a bases de datos en producción real.

Investigación de Operaciones: Modelo PLEB y Demostración Algorítmica

Docente: Ing. Lucía Margarita Mestre Tapia 📄 Ver Entregable IO (.pdf)

Asignación algorítmica de centros veterinarios mediante Programación Lineal Entera Binaria acoplada a la fórmula trigonométrica del Semiverseno (Haversine).

Formulación Matemática Formal (PLEB)

Función Objetivo:
Min Z = ∑_{i ∈ I} (d_i × X_i)
Restricciones del Sistema:
∑ X_i = 1 Selección Única: Asignar exactamente 1 sede factible.
X_i ≤ A_i Operatividad: Solo clínicas con estado APROBADA (A_i = 1).
d_i·X_i ≤ D_max Radio de Cobertura: Desplazamiento máximo permitido.
X_i ∈ {0,1}, d_i ≥ 0 Condiciones de binariedad y no negatividad geodésica.

Fórmula Geodésica de Haversine

Calcula la distancia ortodrómica sobre la esfera terrestre entre las coordenadas del usuario (lat_u, lon_u) y cada clínica (lat_i, lon_i):

d_i = 2 · R · arcsin( √( sin²(Δlat/2) + cos(lat_u) · cos(lat_i) · sin²(Δlon/2) ) )
// Radio terrestre medio: R = 6.371 km

Implementado en Java en OptimizacionServiceImpl.java e integrado con mapas interactivos Leaflet en la ruta /usuario/optimizacion-clinicas.

Simulador Didáctico de Optimización PLEB (Cartagena de Indias)

Ingresa unas coordenadas de prueba en Cartagena para observar cómo el algoritmo evalúa las restricciones y minimiza la distancia.

Arquitectura de 5 Capas de ClinicaApp

Estructura de integración desacoplada entre backend transaccional, servicios cognitivos de IA generativa y repositorio analítico.

CAPA 1

Cliente / Frontend

Thymeleaf UI, JavaScript reactivo, Web Speech API (Voz STT/TTS), cliente REST.

CAPA 2

Backend Spring Boot

Spring Boot 3.5 (Java 21), SecurityConfig, NovaAIController, IOptimizacionService.

CAPA 3

Persistencia NoSQL

MongoDB Atlas 7.0, MongoRepository, Aggregation Framework, 7 colecciones.

CAPA 4

Proveedor LLM

Groq Cloud API (Llama 3.3 70B Versatile) + Motor de contingencia MOTOR_LOGICO.

CAPA 5

Analítica & BI

6 Datasets CSV (Kimball), Esquema Estrella con 3.469 hechos, métricas DAX.
